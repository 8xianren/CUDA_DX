# 图形着色器补充 2：坐标空间与 HLSL/GLSL 矩阵

## 一句话目标

理解模型空间 → 世界空间 → 观察空间 → 裁剪空间 → NDC → 屏幕的完整链条，并能解释为什么常见 HLSL 写成 `mul(position, matrix)`，而 GLSL 写成 `matrix * position`。

## 1. 游戏开发直觉：同一个点换了几套“坐标系”

可以把一个模型顶点想成关卡编辑器里的一把椅子上的某个顶点：

```text
模型空间（Local/Object）
  顶点相对于模型原点的位置
        ↓ Model / ObjectToWorld
世界空间（World）
  顶点在关卡中的位置
        ↓ View / WorldToView
观察空间（View/Camera）
  顶点相对于摄像机的位置
        ↓ Projection / ViewToClip
裁剪空间（Clip）
  透视投影尚未除以 w 的坐标
        ↓ 透视除法 xyz / w
NDC（Normalized Device Coordinates）
  通常 x/y ∈ [-1,1]，深度范围由图形 API 约定
        ↓ Viewport Transform
屏幕像素坐标
```

这几次变换不是 CUDA 特有的，也不是 HLSL/GLSL 独自发明的；它们是光栅化管线需要的几何约定。矩阵只是把平移、旋转、缩放、相机和投影组合成可批量执行的线性代数运算。

## 2. 点和方向为什么都要带 `w`

齐次坐标用四维向量表示三维对象：

```text
点（point）     (x, y, z, 1)
方向（vector）  (x, y, z, 0)
```

平移矩阵只应该移动点，不应该移动方向。齐次坐标正是通过 `w` 区分这两种语义：

```text
M × (position, 1) → 旋转/缩放 + 平移
M × (direction, 0) → 旋转/缩放，不受平移影响
```

当前粒子 shader 没有完整的相机矩阵，直接把 `positionSize.xy` 当成 NDC 附近的坐标，并写入：

```hlsl
float4(positionSize.xy + local * radius, positionSize.z, 1.0)
```

最后一个 `1.0` 表示这是一个位置点。由于 `w=1`，后面的透视除法不会改变 x/y。这相当于把“模型/世界/观察/投影”几步提前在 CPU/CUDA 或示例逻辑中简化掉了。

## 3. `w` 还负责透视除法

Vertex Shader 输出裁剪空间位置 `p_clip=(x_c,y_c,z_c,w_c)` 后，光栅化前会做：

```text
ndc.x = x_c / w_c
ndc.y = y_c / w_c
ndc.z = z_c / w_c
```

因此透视投影中远处物体会变小：投影矩阵让 `w_c` 随深度变化，除法自然产生“远小近大”。

本例所有粒子顶点都使用 `w=1`，所以没有透视缩放；粒子大小只由 `positionSize.w` 和宽高比修正控制。这正适合当前的屏幕空间粒子示例，但不是完整 3D 相机方案。

## 4. HLSL 里的矩阵乘法

下面是一个明确采用“行向量写法”的 HLSL 示例：

```hlsl
// row_major 明确告诉编译器 cbuffer 中如何排布矩阵元素。
// 它解决的是内存布局/上传约定，不改变 mul 的数学定义。
cbuffer TransformConstants : register(b0)
{
    row_major float4x4 objectToWorld;
    row_major float4x4 worldToView;
    row_major float4x4 viewToClip;
};

float4 VSMain(float3 localPosition : POSITION) : SV_Position
{
    // w=1：这是位置点，所以 Model 矩阵的平移会生效。
    const float4 localPoint = float4(localPosition, 1.0);

    // HLSL 的 mul(vector, matrix) 把 vector 当作行向量。
    const float4 worldPoint = mul(localPoint, objectToWorld);
    const float4 viewPoint  = mul(worldPoint, worldToView);
    const float4 clipPoint  = mul(viewPoint, viewToClip);
    return clipPoint;
}
```

这段代码表达的是：

```text
p_clip = ((p_local · M) · V) · P
```

如果预先合并矩阵，等价于：

```hlsl
const float4x4 localToClip =
    mul(mul(objectToWorld, worldToView), viewToClip);
const float4 clipPoint = mul(localPoint, localToClip);
```

这里最容易犯的错是把矩阵顺序倒过来。矩阵乘法一般不可交换：

```text
M · V ≠ V · M
```

先旋转再平移，和先平移再旋转，结果通常不同。

## 5. GLSL 的矩阵乘法

GLSL 常用列向量写法：

```glsl
#version 450

// std140 是 Uniform Buffer 的布局规则；binding=0 是资源接口编号。
layout(std140, binding = 0) uniform TransformConstants {
    mat4 objectToWorld;
    mat4 worldToView;
    mat4 viewToClip;
};

layout(location = 0) in vec3 localPosition;

void main()
{
    // GLSL 的 vec4 是列向量，矩阵放在左边。
    gl_Position = viewToClip * worldToView * objectToWorld
                * vec4(localPosition, 1.0);
}
```

数学表达式是：

```text
p_clip = P · V · M · p_local
```

注意从右向左读：最右边的 `M` 先作用于点，然后是 `V`，最后是 `P`。

## 6. 关键边界：数学方向 ≠ 内存布局

这是 HLSL/GLSL 矩阵最重要的防混淆规则。

### 数学方向

决定你写：

```text
HLSL 常见：mul(v, M)   // 行向量
GLSL 常见：M * v       // 列向量
```

### 内存布局

决定矩阵元素在 Constant/Uniform Buffer 中如何排列、CPU 该如何上传。常见术语：

- HLSL `row_major` / `column_major`：Shader 侧的矩阵存储布局修饰符。
- GLSL `std140` / `std430`：接口块成员的对齐与布局规则；矩阵通常按列向量对齐。
- CPU 数学库的默认约定：DirectXMath、GLM、自定义矩阵类可能各不相同。

因此不能说“GLSL 永远列主序，所以只要转置一次就行”。必须同时检查：

1. CPU 构造矩阵时采用的向量方向；
2. Shader 中的乘法方向；
3. Buffer 的布局修饰符与对齐；
4. 上传 API 是否按行/列连续写入；
5. 投影矩阵的深度范围和左右手坐标约定。

“行/列主序”这个词经常同时被用来描述数学向量约定和内存排布，实际排错时必须把两层分开。

## 7. 矩阵元素下标的另一个陷阱

GLSL 的矩阵下标通常按“列、行”访问：

```glsl
mat4 m;
float x = m[column][row];
```

HLSL 通常按“行、列”理解下标：

```hlsl
float4x4 m;
float x = m[row][column];
```

这与 Shader 里选择行向量/列向量的乘法习惯相关，但仍不能代替对实际 Buffer 上传布局的检查。

## 8. D3D12、OpenGL、Vulkan 的 NDC 差异

常见的 x/y 范围大致都是 `[-1,1]`，但深度和屏幕 Y 方向不能想当然：

| API | 常见 NDC 深度范围 | 额外注意 |
|---|---|---|
| D3D12 | `z ∈ [0,1]` | 当前项目使用此约定 |
| OpenGL | `z ∈ [-1,1]` | 与 D3D 投影矩阵不能直接互换 |
| Vulkan | `z ∈ [0,1]` | viewport/Y 翻转约定需结合管线设置 |

所以从 D3D12 迁移 GLSL/Vulkan 时，不能只把 `float4` 改成 `vec4`；投影矩阵、深度范围和 viewport 约定也要一起核对。

## 9. 回到当前粒子 shader

当前 VS：

```hlsl
const float4 positionSize = gPositions[instanceId];
const float2 local = corners[vertexId];

output.clipPosition = float4(
    positionSize.xy + local * screenCorrectedRadius,
    positionSize.z,
    1.0);
```

它隐含了几个简化假设：

```text
positionSize.xy 已经接近 NDC
z 直接作为裁剪空间深度
w 固定为 1，不使用透视缩放
没有 world/view/projection Constant Buffer
```

这不是“没有坐标变换”，而是把完整 3D 变换简化成了一个屏幕空间 billboard。后续如果要把粒子放进真正的 3D 世界，需要至少增加：

```text
粒子世界位置
相机 View 矩阵
Projection 矩阵
粒子朝向相机的 billboard 逻辑
```

CUDA 仍然可以只负责生产世界位置/速度；矩阵和相机通常属于渲染侧的 Constant Buffer/Uniform Buffer。

## 10. 常见错误清单

### 错误 1：把 `mul(v, M)` 改成 `mul(M, v)`，只看起来“更像数学书”

HLSL 两种写法的向量方向不同，不能只交换参数而不调整矩阵构造和上传约定。

### 错误 2：看到转置就以为能修复所有问题

转置可能修复内存布局不匹配，但不能修复错误的矩阵乘法顺序、错误的左右手坐标系或 D3D/GL 深度范围。

### 错误 3：把方向向量的 `w` 写成 1

法线、速度、光照方向如果带 `w=1`，会被错误地施加平移。位置点才用 `w=1`。

### 错误 4：把 NDC 当屏幕像素

`(-1,-1)` 和 `(1,1)` 是归一化设备坐标边界，不是像素坐标 `(0,0)` 和 `(width,height)`。Viewport 变换由图形管线完成。

### 错误 5：D3D12 的投影矩阵直接拿给 OpenGL

深度范围不同，通常需要调整投影矩阵或使用适配矩阵；不能只改 shader 语法。

## 11. 动手练习

1. 在当前 HLSL 中把 `positionSize.z` 改成 `0.0`，观察深度值变化；理解本例没有 Depth Buffer 时它对最终颜色的影响很小，但它仍是 `SV_Position` 的深度分量。
2. 把 `w` 从 `1.0` 改成 `2.0`，预测粒子在透视除法后 x/y 会缩小为原来的一半，再运行验证。这个实验直接证明 `SV_Position` 的 `w` 不是普通 padding。
3. 手写一组 2D 变换：先把点旋转 90°，再平移 `(1,0)`；分别用“先旋转后平移”和“先平移后旋转”计算结果，确认矩阵不可交换。
4. 对照 HLSL 与 GLSL 示例，在纸上标出三件事：向量位于乘法左边还是右边、矩阵实际应用顺序、矩阵 Buffer 的布局规则。不要把它们合并成一个“行列主序”结论。

## 12. 小结

- 坐标变换的主链是 Local → World → View → Clip → NDC → Screen。
- `w=1` 表示位置点，`w=0` 表示方向；透视除法使用 `xyz/w`。
- HLSL 常见行向量写法：`mul(v, M)`；GLSL 常见列向量写法：`M * v`。
- 矩阵乘法方向和矩阵内存布局是两件正交的事；转置不是万能修复。
- D3D12/OpenGL/Vulkan 在 NDC 深度和 viewport 约定上存在差异。
- 当前粒子 shader 是屏幕空间简化版，`positionSize.xy` 已经接近 NDC，因此没有真正的相机矩阵。
