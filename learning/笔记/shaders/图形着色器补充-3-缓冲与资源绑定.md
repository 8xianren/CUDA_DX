# 图形着色器补充 3：缓冲资源与绑定模型

## 一句话目标

学完这一节，你应该能回答三件事：

1. 为什么相机矩阵通常放在 Constant/Uniform Buffer，而粒子数组放在 StructuredBuffer/SSBO？
2. HLSL 的 `register(b0/t0/u0)`、GLSL/Vulkan 的 `binding`，与 D3D12 的 descriptor heap 到底是什么关系？
3. CUDA 写入的 device pointer 为什么不能直接写进 HLSL，而必须先变成 D3D12 资源的 SRV/UAV 视图？

本节只讲“资源接口和布局”。矩阵具体怎么构造，已经在上一节《坐标空间与矩阵》中讲过。

## 1. 先建立直觉：资源绑定像渲染管线的“插槽表”

把一帧渲染想象成给材质和 shader 准备一张拍摄清单：

```text
shader 代码：我需要 b0 的相机参数、t0 的粒子数组
        ↓
CPU/D3D12：把相机常量和粒子资源的“视图”放进对应插槽
        ↓
GPU：shader 按插槽编号取数据
```

这里的 `b0`、`t0` 不是显存地址，也不是 C++ 指针。它们是 shader 接口中的逻辑编号：

- `b`：constant buffer view（CBV），适合小而频繁变化的参数；
- `t`：shader resource view（SRV），只读资源；
- `u`：unordered access view（UAV），可读写资源；
- sampler 通常使用 `s` 插槽。

游戏里的类比是：

- root signature / descriptor set：规定“片场有哪几类插槽”；
- descriptor：插槽里的资源卡片，写着资源地址、格式、元素数量、步长等元数据；
- shader 中的 `register(t0)` 或 `binding=0`：读取哪一个插槽；
- 真正的 buffer allocation：片场后面的仓库。

因此，“绑定编号”与“显存地址”是两层完全不同的抽象。驱动在执行命令时，才会沿着 descriptor 找到实际资源。

## 2. 四种常见缓冲接口

### 2.1 HLSL `cbuffer`：常量缓冲

```hlsl
cbuffer FrameConstants : register(b0)
{
    // 4x4 矩阵通常占 4 个 16-byte 常量寄存器，即 64 字节。
    // 这里使用 row_major 只是明确 Buffer 中的矩阵排布；它不等于
    // “所有 HLSL 矩阵都必须这样乘”，乘法方向仍由 mul 的两个参数决定。
    row_major float4x4 viewProjection;

    // float2 + float2 恰好可以放进同一个 16-byte 常量寄存器。
    float2 viewportSize;
    float2 inverseViewportSize;
};

float4 VSMain(float3 worldPosition : POSITION) : SV_Position
{
    // 这是位置点，w=1，因此平移和透视投影都按“点”的语义生效。
    return mul(float4(worldPosition, 1.0), viewProjection);
}
```

`cbuffer` 的特点：

- shader 通过 CBV 只读访问；
- 适合帧常量、相机矩阵、时间、视口大小、材质参数；
- 通常一个 draw/dispatch 会复用同一组参数；
- D3D12 创建 CBV 时，`SizeInBytes` 必须满足 256 字节对齐，即使真正的数据只有几十字节。

最后一点很容易漏掉：HLSL 常量变量有自己的 16-byte packing 规则，而 D3D12 CBV 又有 256-byte 起始地址/大小约束。前者决定成员在 cbuffer 内的偏移，后者决定这块常量资源能否作为 CBV 绑定。

### 2.2 HLSL `StructuredBuffer`：结构化只读数组

```hlsl
struct ParticleGpu
{
    // 采用 float4 而不是 float3，方便 CUDA、D3D12 和 shader 共享明确的 16-byte 元素。
    float4 positionSize;
    float4 velocityMass;
    float4 color;
};

// t0 是逻辑资源槽；[index] 的 index 是结构化元素索引，不是字节偏移。
StructuredBuffer<ParticleGpu> gParticles : register(t0);

ParticleGpu p = gParticles[instanceId];
```

特点：

- 元素步长由资源视图的 `StructureByteStride` 描述；
- shader 用结构体数组的方式索引，适合粒子、实例数据、骨骼数据等大量元素；
- 视图可以只覆盖一个大 buffer 的子区间；
- `StructuredBuffer` 是只读的，计算 shader 要写必须使用 `RWStructuredBuffer` 和 UAV。

### 2.3 `RWStructuredBuffer`：无序读写数组

```hlsl
RWStructuredBuffer<ParticleGpu> gParticlesOut : register(u0);

[numthreads(256, 1, 1)]
void CSMain(uint3 dispatchThreadId : SV_DispatchThreadID)
{
    const uint i = dispatchThreadId.x;
    // UAV 允许多个线程按任意顺序写不同元素；若多个线程写同一元素，
    // 仍然会有数据竞争，绑定成 UAV 不会自动提供原子性或全局同步。
    gParticlesOut[i].positionSize.xy += float2(0.001, -0.0005);
}
```

`u0` 只表示“这是一个 UAV 槽位”。它不表示线程之间已经同步，也不表示跨 command queue 的所有权已经交接；后两件事分别需要 shader 内同步/原子语义，以及 API 间的 fence/资源状态管理。

### 2.4 GLSL 对照：Uniform Buffer、SSBO

```glsl
#version 450

// std140：Uniform Buffer 的布局规则。binding=0 是逻辑绑定点。
layout(std140, binding = 0) uniform FrameConstants {
    mat4 viewProjection;
    vec2 viewportSize;
    vec2 inverseViewportSize;
};

struct ParticleGpu {
    // 使用 vec4 让跨 API 的 16-byte 元素边界明确，避免 vec3 padding 陷阱。
    vec4 positionSize;
    vec4 velocityMass;
    vec4 color;
};

// std430 常用于 SSBO；相较 std140，它对数组/结构体的部分填充更宽松，
// 但不能因此假定所有 vec3 都能安全地按 12 字节跨 API 共享。
layout(std430, binding = 1) readonly buffer ParticleBuffer {
    ParticleGpu particles[];
};

void main()
{
    gl_Position = viewProjection * vec4(particles[gl_InstanceID].positionSize.xyz, 1.0);
}
```

HLSL 的 `register(t0)` 和 GLSL 的 `binding=1` 都是“接口编号”，但编号空间和布局规则由各 API 定义。迁移 shader 时，不能只把关键字机械替换。

## 3. 为什么相机参数和粒子数组要分开

假设每帧有 4096 个粒子，但相机矩阵只有一套：

```text
相机参数：一帧更新一次，所有顶点/实例重复读取
粒子数组：每个实例读取不同元素，数量大，可能由 CUDA 每步更新
```

把它们分成 CBV 和 SRV 有四个原因：

1. **更新频率不同**：相机参数常常每帧改；粒子数组可能由 CUDA 追赶多个固定时间步。
2. **访问模式不同**：常量适合广播/缓存；结构化数组适合按实例索引。
3. **大小约束不同**：CBV 有常量 buffer 的对齐与 packing 规则；SRV 更适合大容量数组。
4. **读写权限不同**：渲染 VS 通常只读粒子 SRV；CUDA/compute 阶段写入时要通过 UAV 或外部内存映射，并用 fence 交接。

这不是说 GPU 一定使用两种完全不同的物理显存。它们可以指向同一 allocation 的不同 view，区别在于 shader 接口和访问规则。

## 4. HLSL 的绑定链：register → root signature → descriptor heap

当前项目的真实链条如下：

```text
HLSL: gPositions : register(t0)
HLSL: gColors    : register(t1)
              ↓
D3D12 root signature：一个 SRV range，覆盖 t0、t1
              ↓
shader-visible CBV_SRV_UAV heap：连续放两个 SRV descriptor
              ↓
SetGraphicsRootDescriptorTable(0, heap 起始 GPU handle)
              ↓
VS 用 instanceId 读取 t0/t1
```

当前实现可直接对照：

- `learning/sandbox/particles/d3d12_static_particles.hlsl:7-13`：两个 `StructuredBuffer<float4>`；
- `learning/sandbox/particles/d3d12_static_particles.cu:369-387`：root signature 的 SRV range；
- `learning/sandbox/particles/d3d12_static_particles.cu:612-643`：创建两个 SRV，并让 `t1` 从 `2*N` 个 `float4` 处开始；
- `learning/sandbox/particles/d3d12_static_particles.cu:688-694`：绑定 root signature、shader-visible heap 和 descriptor table；
- `learning/sandbox/particles/d3d12_static_particles.cu:696-701`：`DrawInstanced(6, N, 0, 0)` 让 VS 用实例编号索引粒子。

关键的 D3D12 片段是：

```cpp
D3D12_SHADER_RESOURCE_VIEW_DESC srv_description{};
srv_description.Shader4ComponentMapping =
    D3D12_DEFAULT_SHADER_4_COMPONENT_MAPPING;
srv_description.Format = DXGI_FORMAT_UNKNOWN;
srv_description.ViewDimension = D3D12_SRV_DIMENSION_BUFFER;
srv_description.Buffer.FirstElement = 0;
srv_description.Buffer.NumElements = kParticleCount;
srv_description.Buffer.StructureByteStride = sizeof(float4);

// 第一个 descriptor 对应 register(t0)。
// 如果 C++ 变量是 ComPtr<ID3D12Resource>，传给 D3D12 API 时取原始接口指针。
device->CreateShaderResourceView(particle_buffer.Get(), &srv_description, cpu_handle);

// 第二个 descriptor 对应 register(t1)。
// FirstElement 以 float4 元素计数，不是 byte offset。
srv_description.Buffer.FirstElement = 2ull * kParticleCount;
device->CreateShaderResourceView(particle_buffer.Get(), &srv_description,
                                 cpu_handle_next);
```

这里有三个必须同时匹配的事实：

1. shader 认为元素类型是 `float4`；
2. SRV 认为每个元素步长是 `sizeof(float4)`；
3. `FirstElement` 按这个步长解释，所以 `2*N` 正好跳过 position 和 velocity。

任何一项不匹配，都可能出现“画面能显示但颜色错位”“只有部分粒子正确”这类比直接崩溃更难排查的问题。

## 5. `register` 编号为什么不是显存地址

D3D12 把资源描述拆成几层，是为了让命令录制和资源复用更灵活：

```text
资源 allocation：实际的 Default/Upload/共享 Heap 内存
        ↓
SRV/CBV/UAV descriptor：描述如何解释这块内存
        ↓
descriptor heap：GPU 可见的 descriptor 数组
        ↓
root descriptor table：告诉 shader 从 heap 的哪一项开始找
        ↓
register(t0/b0/u0)：shader 访问的逻辑槽
```

所以 `t0` 里可以换成另一块资源，只要新的 descriptor 仍然满足 shader 期待的格式、步长和生命周期。反过来，拿一个 CUDA device pointer 填到 `t0` 并不成立：HLSL 不认识 CUDA runtime 的 pointer 类型，D3D12 也需要一个它自己的资源和视图。

## 6. CUDA 外部内存如何接到这条链上

当前综合项目的所有权/视图链可以画成：

```text
D3D12 committed shared buffer
        │  导出 NT handle
        ▼
cudaImportExternalMemory
        │
cudaExternalMemoryGetMappedBuffer → CUDA device pointer
        │                              │
        │                              └─ kernel 写 position/velocity/color
        │
        └─ 同一 D3D12 resource 仍然创建 SRV(t0/t1)
                                           │
                             D3D12 command queue + VS 读取
```

“同一 allocation”不等于“可以同时读写”。当前项目用 external timeline fence 规定顺序：

```text
CUDA 等待 D3D12 完成 → CUDA kernel 写 → signal CUDA-ready
D3D12 等待 CUDA-ready → VS 读 → signal D3D-done
```

Fence 负责跨 API 的先后关系；D3D12 resource barrier 负责 D3D12 内部的资源状态描述；descriptor 负责 shader 如何解释资源。三者职责不同，不能互相替代。

## 7. 绑定编号的跨 API 对照

| 语义 | HLSL / D3D12 | GLSL / OpenGL | Vulkan GLSL |
|---|---|---|---|
| 常量参数 | `cbuffer : register(b0)` + CBV | `layout(std140, binding=0) uniform` | `layout(set=0,binding=0) uniform` |
| 只读结构化数组 | `StructuredBuffer<T> : register(t0)` + SRV | `layout(std430,binding=1) readonly buffer` | `layout(set=0,binding=1) readonly buffer` |
| 读写结构化数组 | `RWStructuredBuffer<T> : register(u0)` + UAV | `buffer` / image 等可写接口 | `buffer` / storage image |
| 采样器 | `register(s0)` | `layout(binding=...) sampler` | `layout(set=...,binding=...) sampler` |

Vulkan 多了 `set` 这一层：可以把 `set` 理解为较大的 descriptor set 分组，`binding` 是组内插槽。D3D12 没有完全同名的 set 概念，而是通过 root parameters、descriptor ranges 和 descriptor heaps 组合出类似的接口组织方式。

## 8. 布局陷阱：CBV packing、`std140`、`std430`、StructuredBuffer stride

### 8.1 HLSL cbuffer 的 16-byte packing

不要直接把任意 C++ struct 的 `sizeof` 当作 cbuffer 成员布局。一个安全的教学写法是主动按 16 字节组织：

```cpp
struct FrameConstantsCpu {
  // 64 字节，对应 HLSL 的 float4x4。
  DirectX::XMFLOAT4X4 view_projection;

  // 两个 float2 共 16 字节，正好对应一个常量寄存器。
  DirectX::XMFLOAT2 viewport_size;
  DirectX::XMFLOAT2 inverse_viewport_size;
};

static_assert(sizeof(FrameConstantsCpu) == 80);
```

上传到 D3D12 时，放入一个按 256 字节对齐的常量资源/子分配：

```cpp
// 真实 CBV 大小需要向上取整到 256 的倍数；未使用的尾部字节可以置零。
constexpr UINT kCbvSize =
    (sizeof(FrameConstantsCpu) + 255u) & ~255u;
```

### 8.2 GLSL `std140` / `std430`

- `std140` 适合 Uniform Buffer，规则保守，很多数组/结构体成员按 16-byte 粒度对齐；
- `std430` 常用于 SSBO，允许一部分数组/结构体减少填充；
- `vec3` 在跨编译器、跨 API、跨 CPU 结构体共享时最容易制造错位，教学和互操作代码优先使用 `vec4` 或显式 padding；
- 不能用“GLSL 总是列主序”替代对齐检查。矩阵乘法方向、矩阵存储、块布局和 CPU 上传是四个问题。

### 8.3 StructuredBuffer 与 SSBO 的 stride

StructuredBuffer/SSBO 的数组元素有“结构体步长”。CUDA 端、D3D12 SRV/UAV、HLSL 结构体、GLSL block layout 必须采用同一份 ABI（应用二进制接口）约定。

当前项目使用三个连续的 `float4[N]` 区段，优点是：

```text
position[N]   : 16*N 字节
velocity[N]   : 16*N 字节
color[N]      : 16*N 字节
```

CUDA 通过 base pointer + 元素偏移访问，D3D12 则为不同区段建立不同 SRV。这种 SoA 设计同时兼顾了 CUDA 连续访存和 shader 按实例取 position/color 的接口清晰度。

### 练习 B：增加一个相机 CBV 的接口设计

```hlsl

    row_major float4x4 viewProjection;
```

思考 D3D12 root signature 是否要再加一个 `D3D12_DESCRIPTOR_RANGE_TYPE_CBV` range；CBV heap 是否仍然是 `CBV_SRV_UAV` 类型；每帧更新相机参数时，为什么通常会使用环形常量缓冲而不是覆盖 GPU 仍在读取的同一份内存。

## 10. 小结

- `cbuffer/Uniform Buffer` 是小而频繁更新的只读参数；`StructuredBuffer/SSBO` 是大量结构化元素；UAV/可写 SSBO 才允许 shader 写入。
- `register`、`binding` 是逻辑接口编号，不是 CUDA pointer，也不是显存地址。
- D3D12 的 root signature 规定接口形状，descriptor heap 保存 GPU 可见 descriptor，root descriptor table 把二者接起来。
- SRV 的 `FirstElement` 按结构化元素计数；`StructureByteStride`、shader 元素类型和 CPU/CUDA 数据布局必须一致。
- HLSL cbuffer 的 16-byte packing、D3D12 CBV 的 256-byte 对齐、GLSL 的 `std140/std430` 是不同层次的约束。
- CUDA external memory pointer 与 D3D12 SRV 可以指向同一 allocation，但 fence、resource barrier 和 descriptor 分别负责同步、状态和解释方式。
